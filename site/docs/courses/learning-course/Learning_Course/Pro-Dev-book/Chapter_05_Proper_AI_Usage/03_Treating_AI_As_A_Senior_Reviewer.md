# 🧑‍🏫 Treating AI As A Senior Reviewer

### 🗣️ The Socratic Dialogue

One of the most profound shifts you can make as a developing engineer is to stop treating Large Language Models (LLMs) like Google or StackOverflow, and start treating them like a highly-patient, infinitely knowledgeable **Senior Technical Mentor**.

When you ask an LLM for "The Answer," it gives you a block of code. 
When you ask an LLM to "Explain the tradeoff," it gives you an architectural lesson.

---

### 🎓 The Prompting Paradigm Shift

If you are a junior or mid-level developer, your primary goal is to close the gap between your current knowledge and the knowledge of the Senior Engineers who review your Pull Requests. AI can simulate this process perfectly if prompted correctly.

#### ❌ The Output-Oriented Prompt (Bad)
> *"Copilot, write a unit test for my User Registration controller."*

This prompt asks for the physical labor (the typing) to be done for you. It robs you of the opportunity to learn *how* to mock a database, *how* to assert an event was dispatched, and *how* to structure a test properly.

#### ✅ The Insight-Oriented Prompt (Pro)
> *"Act as a Lead Test Engineer. I have attached my User Registration controller. I am new to testing in Laravel. Do not write the tests for me. Instead, provide a bulleted list of the exact 5 scenarios I need to test (e.g., Happy Path, Database Failure, Missing Data), and briefly explain why mocking the Mail facade is necessary here."*

This prompt forces the AI into a pedagogical role. It gives you the high-level roadmap and the architectural theory, forcing *you* to do the actual syntax labor.

---

### 🔍 Conducting Your Own Code Reviews

Do not wait for your Lead Developer to tear apart your Pull Request on GitHub. You should proactively run your own local code reviews using AI before you ever commit your code.

#### 1. The SOLID Principle Review
*   **Prompt:** *"Review this controller class. Evaluate it strictly against SOLID principles. Am I violating the Single Responsibility Principle by putting my payment processing logic in the `store()` method? Is there a cleaner way to use Dependency Injection here to make it more testable?"*

#### 2. The N+1 Query Audit
*   **Prompt:** *"Act as a Database Administrator. Review this Laravel Eloquent logic. Am I accidentally triggering an N+1 query issue when looping through these `Orders` to get the `User` email? Show me how to use Eager Loading optimize this."*

#### 3. The Security & Edge-Case Audit (Pessimistic Design)
*   **Prompt:** *"Review this checkout logic. Assume a malicious user is trying to manipulate the cart total, or that the external Stripe API takes 15 seconds to respond. Point out exactly where my code will break under those extreme conditions and suggest pessimistic architectural patterns to secure it."*

---

### 🧠 The "Explain It Like..." Technique

When you encounter a block of code (either written by a coworker or generated by an AI) that you do not fundamentally understand, do not blindly execute it.

Use the AI to dissect the complexity:
*   *"Explain how Laravel's Service Container works, but use an analogy of a highly-organized restaurant kitchen to make it simple."*
*   *"I see this code uses the `yield` keyword in PHP. I've never seen that before. Explain what a Generator is, and give me a 3-line example of why it saves memory over a standard `return` array."*

**Summary:** Your goal with AI is not to write code faster; it is to extract senior-level wisdom faster. By prompting the AI to review, critique, and explain, you turn every single coding session into a 1-on-1 masterclass with an expert architect.
