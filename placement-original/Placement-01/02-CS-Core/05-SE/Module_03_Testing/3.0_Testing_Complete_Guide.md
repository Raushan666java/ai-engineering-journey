## 📚 Detailed Topics

### 3.1 Fundamentals of Software Testing

#### 3.1.1 Testing Principles and Psychology
**Seven Principles of Testing**
1. Testing shows presence of defects, not their absence
2. Exhaustive testing is impossible
3. Early testing saves time and money
4. Defects cluster together
5. Pesticide paradox - tests lose effectiveness over time
6. Testing is context dependent
7. Absence-of-errors fallacy

**Psychology of Testing**
- Tester vs. developer mindset
- Confirmation bias and its impact
- Independent testing benefits
- Constructive vs. destructive testing
- Error-prone areas identification

#### 3.1.2 Testing Process and Activities
**Fundamental Test Process**
- Test planning and control
- Test analysis and design
- Test implementation and execution
- Evaluating exit criteria and reporting
- Test closure activities

**Test Documentation**
- Test policy and strategy
- Test plans and procedures
- Test cases and scripts
- Test data and environments
- Test reports and metrics

### 3.2 Testing Levels

#### 3.2.1 Unit Testing
**Definition and Scope**
- Testing individual components in isolation
- White-box testing approach
- Developer responsibility
- Fast feedback and early defect detection

**Unit Testing Best Practices**
- Test one thing at a time
- Use descriptive test names
- Arrange-Act-Assert pattern
- Independent and repeatable tests
- Fast execution (< 1 second per test)

**Unit Testing Frameworks**
- **Java**: JUnit 5, TestNG, Mockito
- **Python**: pytest, unittest, mock
- **JavaScript**: Jest, Mocha, Jasmine
- **C#**: NUnit, xUnit, MSTest
- **C++**: Google Test, Catch2

**Code Coverage Metrics**
- Statement coverage (aim for 80%+)
- Branch coverage (aim for 70%+)
- Function coverage
- Path coverage
- Modified Condition/Decision Coverage (MC/DC)

#### 3.2.2 Integration Testing
**Types of Integration Testing**
- **Big Bang**: All components integrated simultaneously
- **Incremental**: Components integrated one by one
  - Top-down approach with stubs
  - Bottom-up approach with drivers
  - Sandwich/hybrid approach

**Integration Strategies**
- API testing and contract validation
- Database integration testing
- Service integration testing
- End-to-end workflow testing
- Third-party service integration

**Tools and Techniques**
- Postman for API testing
- SoapUI for web services
- Docker for environment consistency
- Test containers for database testing
- Service virtualization for dependencies

#### 3.2.3 System Testing
**System Testing Types**
- **Functional Testing**: Feature validation
- **Performance Testing**: Load, stress, volume
- **Security Testing**: Vulnerability assessment
- **Usability Testing**: User experience validation
- **Compatibility Testing**: Browser, OS, device
- **Recovery Testing**: Failure and recovery scenarios

**Non-Functional Testing**
- **Performance Testing**:
  - Load testing: Normal expected load
  - Stress testing: Beyond normal capacity
  - Volume testing: Large amounts of data
  - Spike testing: Sudden load increases
  - Endurance testing: Extended periods
- **Security Testing**:
  - Authentication and authorization
  - SQL injection and XSS vulnerabilities
  - Data encryption and protection
  - Session management
  - Input validation

#### 3.2.4 Acceptance Testing
**Types of Acceptance Testing**
- **User Acceptance Testing (UAT)**: End-user validation
- **Business Acceptance Testing (BAT)**: Business requirement validation
- **Alpha Testing**: Internal testing by organization
- **Beta Testing**: External testing by limited users
- **Contract Acceptance Testing**: Contractual requirement validation

**Acceptance Criteria**
- INVEST criteria for user stories
- Given-When-Then format
- Testable and measurable criteria
- Business value alignment
- Risk-based prioritization

### 3.4 Test-Driven Development (TDD)

#### 3.4.1 TDD Process and Principles
**Red-Green-Refactor Cycle**
1. **Red**: Write failing test first
2. **Green**: Write minimal code to pass test
3. **Refactor**: Improve code while keeping tests green

**TDD Benefits**
- Better code design and architecture
- Higher test coverage (95%+)
- Reduced debugging time
- Living documentation through tests
- Confidence in code changes

**TDD Best Practices**
- Write tests before production code
- Keep tests simple and focused
- Use descriptive test names
- Test behavior, not implementation
- Maintain fast test execution

#### 3.4.2 TDD Implementation
**Test Structure**
```
// Arrange: Set up test data and conditions
// Act: Execute the code under test
// Assert: Verify the expected outcome
```

**Common TDD Patterns**
- **Fake It**: Return constants first, then generalize
- **Triangulation**: Use multiple examples to drive generalization
- **Obvious Implementation**: Implement directly when solution is clear
- **Test List**: Maintain list of tests to write

**TDD Challenges and Solutions**
- Legacy code integration: Characterization tests
- Database testing: In-memory databases, test containers
- UI testing: Page object pattern, component testing
- External dependencies: Mocking and stubbing

#### 3.4.3 Advanced TDD Concepts
**Test Doubles**
- **Dummy**: Objects passed but never used
- **Fake**: Working implementation with shortcuts
- **Stub**: Provides canned answers to calls
- **Spy**: Records information about calls
- **Mock**: Pre-programmed with expectations

**TDD Metrics**
- Test coverage percentage
- Test execution time
- Test failure rate
- Code complexity metrics
- Defect density reduction

### 3.5 Behavior-Driven Development (BDD)

#### 3.5.1 BDD Fundamentals
**BDD Philosophy**
- Focus on behavior rather than testing
- Collaboration between developers, testers, and business
- Ubiquitous language for all stakeholders
- Outside-in development approach

**Given-When-Then Format**
- **Given**: Initial context and preconditions
- **When**: Event or action that triggers behavior
- **Then**: Expected outcome or result
- **And/But**: Additional conditions or outcomes

#### 3.5.2 BDD Tools and Frameworks
**Cucumber Family**
- **Cucumber**: Ruby, Java, JavaScript
- **SpecFlow**: .NET framework
- **Behave**: Python framework
- **Behat**: PHP framework

**Feature File Structure**
```gherkin
Feature: User Login
  As a registered user
  I want to log into the system
  So that I can access my account

  Scenario: Successful login
    Given I am on the login page
    When I enter valid credentials
    Then I should be redirected to dashboard
```

**Step Definitions**
- Mapping Gherkin steps to code
- Parameter passing and data tables
- Scenario outlines for data-driven testing
- Background steps for common setup

#### 3.5.3 BDD Implementation Strategy
**Three Amigos Approach**
- Business Analyst: Defines acceptance criteria
- Developer: Implements functionality
- Tester: Validates behavior

**BDD Process**
1. Discovery: Explore and understand requirements
2. Formulation: Document examples and rules
3. Automation: Implement executable specifications
4. Living Documentation: Maintain up-to-date specs
