## 📚 Detailed Topics

### 4.1 Version Control Fundamentals

#### 4.1.1 Version Control Concepts
**Why Version Control?**
- Track changes over time
- Collaborate with multiple developers
- Maintain project history
- Enable rollback capabilities
- Support parallel development
- Backup and recovery

**Types of Version Control Systems**
- **Local VCS**: RCS, SCCS
- **Centralized VCS**: CVS, Subversion (SVN)
- **Distributed VCS**: Git, Mercurial, Bazaar

**Git Architecture**
- Working directory
- Staging area (index)
- Local repository
- Remote repository
- Git objects: blobs, trees, commits, tags

#### 4.1.2 Git Fundamentals
**Basic Git Commands**
```bash
# Repository initialization
git init
git clone <repository-url>

# Basic workflow
git add <file>
git commit -m "commit message"
git push origin main
git pull origin main

# Status and history
git status
git log --oneline --graph
git diff
git show <commit-hash>
```

**Git Configuration**
```bash
# Global configuration
git config --global user.name "Your Name"
git config --global user.email "your.email@example.com"
git config --global core.editor "code --wait"

# Repository-specific configuration
git config user.name "Project Name"
git config user.email "project@example.com"
```

**Working with Files**
```bash
# File operations
git add .                    # Stage all changes
git add -p                   # Interactive staging
git reset HEAD <file>        # Unstage file
git checkout -- <file>      # Discard changes
git rm <file>               # Remove file
git mv <old> <new>          # Rename file
```

### 4.2 Advanced Git Operations

#### 4.2.1 Branching and Merging
**Branch Management**
```bash
# Branch operations
git branch                   # List branches
git branch <branch-name>     # Create branch
git checkout <branch-name>   # Switch branch
git checkout -b <branch>     # Create and switch
git branch -d <branch>       # Delete branch
git branch -m <old> <new>    # Rename branch
```

**Merging Strategies**
- **Fast-forward merge**: Linear history
- **Three-way merge**: Merge commit created
- **Squash merge**: Combine commits into one
- **Rebase**: Replay commits on different base

```bash
# Merge operations
git merge <branch>           # Merge branch
git merge --no-ff <branch>   # Force merge commit
git merge --squash <branch>  # Squash merge
git rebase <branch>          # Rebase current branch
git rebase -i HEAD~3         # Interactive rebase
```

**Conflict Resolution**
```bash
# Handling merge conflicts
git status                   # Check conflict status
# Edit conflicted files manually
git add <resolved-file>      # Mark as resolved
git commit                   # Complete merge
git merge --abort            # Abort merge
```

#### 4.2.2 Remote Repository Management
**Remote Operations**
```bash
# Remote management
git remote -v                # List remotes
git remote add origin <url>  # Add remote
git remote set-url origin <url> # Change remote URL
git fetch origin             # Fetch changes
git pull origin main         # Fetch and merge
git push origin main         # Push changes
git push -u origin <branch>  # Push and set upstream
```

**Working with Forks**
```bash
# Fork workflow
git remote add upstream <original-repo-url>
git fetch upstream
git checkout main
git merge upstream/main
git push origin main
```

#### 4.2.3 Git History Management
**Viewing History**
```bash
# Log variations
git log --oneline            # Compact log
git log --graph --all        # Visual branch history
git log --author="John"      # Filter by author
git log --since="2 weeks ago" # Time-based filter
git log -p                   # Show patches
git blame <file>             # Line-by-line history
```

**Undoing Changes**
```bash
# Undo operations
git reset --soft HEAD~1      # Undo commit, keep changes staged
git reset --mixed HEAD~1     # Undo commit and staging
git reset --hard HEAD~1      # Undo commit, staging, and changes
git revert <commit-hash>     # Create reverse commit
git cherry-pick <commit>     # Apply specific commit
```

### 4.3 Branching Strategies

#### 4.3.1 Git Flow
**Branch Types**
- **main/master**: Production-ready code
- **develop**: Integration branch for features
- **feature/***: Individual feature development
- **release/***: Release preparation
- **hotfix/***: Critical production fixes

**Git Flow Workflow**
1. Create feature branch from develop
2. Develop feature and commit changes
3. Merge feature back to develop
4. Create release branch from develop
5. Test and fix issues in release branch
6. Merge release to main and develop
7. Tag release on main branch

```bash
# Git Flow commands (with git-flow extension)
git flow init
git flow feature start <feature-name>
git flow feature finish <feature-name>
git flow release start <version>
git flow release finish <version>
git flow hotfix start <hotfix-name>
git flow hotfix finish <hotfix-name>
```

#### 4.3.2 GitHub Flow
**Simplified Workflow**
1. Create branch from main
2. Add commits and push branch
3. Open pull request
4. Discuss and review code
5. Deploy and test
6. Merge to main

**Benefits**
- Simple and lightweight
- Continuous deployment friendly
- Fast feedback loop
- Suitable for web applications

#### 4.3.3 GitLab Flow
**Environment Branches**
- **main**: Development environment
- **pre-production**: Staging environment
- **production**: Production environment

**Release Branches**
- Create release branches for versions
- Cherry-pick fixes to release branches
- Merge releases to production

### 4.4 Code Review Process

#### 4.4.1 Pull Request Best Practices
**Creating Effective Pull Requests**
- Clear and descriptive title
- Detailed description with context
- Link to related issues or tickets
- Include screenshots for UI changes
- Keep changes focused and small
- Self-review before submission

**Pull Request Template**
```markdown
## Description
Brief description of changes

## Type of Change
- [ ] Bug fix
- [ ] New feature
- [ ] Breaking change
- [ ] Documentation update

## Testing
- [ ] Unit tests pass
- [ ] Integration tests pass
- [ ] Manual testing completed

## Checklist
- [ ] Code follows style guidelines
- [ ] Self-review completed
- [ ] Documentation updated
- [ ] No merge conflicts
```

#### 4.4.2 Code Review Guidelines
**Reviewer Responsibilities**
- Understand the context and requirements
- Check for correctness and logic errors
- Verify code style and conventions
- Assess performance implications
- Ensure adequate test coverage
- Provide constructive feedback

**Review Checklist**
- **Functionality**: Does the code work as intended?
- **Readability**: Is the code easy to understand?
- **Maintainability**: Can the code be easily modified?
- **Performance**: Are there any performance issues?
- **Security**: Are there security vulnerabilities?
- **Testing**: Is there adequate test coverage?

**Feedback Guidelines**
- Be specific and actionable
- Explain the "why" behind suggestions
- Use positive and constructive language
- Distinguish between must-fix and nice-to-have
- Acknowledge good practices

#### 4.4.3 Code Review Tools
**GitHub Pull Requests**
- Inline comments and suggestions
- Review approval workflow
- Integration with CI/CD
- Protected branch rules

**GitLab Merge Requests**
- Merge request templates
- Approval rules and policies
- Merge request dependencies
- Security scanning integration

**Other Tools**
- **Crucible**: Atlassian code review tool
- **Review Board**: Web-based code review

### 4.5 Continuous Integration and Deployment

#### 4.5.1 CI/CD Fundamentals
**Continuous Integration (CI)**
- Automated build and test execution
- Early detection of integration issues
- Consistent build environment
- Fast feedback to developers
- Code quality gates

**Continuous Deployment (CD)**
- Automated deployment to environments
- Infrastructure as code
- Blue-green deployments
- Canary releases
- Rollback capabilities

**CI/CD Pipeline Stages**
1. **Source**: Code commit triggers pipeline
2. **Build**: Compile and package application
3. **Test**: Run automated tests
4. **Deploy**: Deploy to target environment
5. **Monitor**: Track application performance

#### 4.5.2 GitHub Actions
**Workflow Configuration**
```yaml
name: CI/CD Pipeline

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    
    steps:
    - uses: actions/checkout@v3
    
    - name: Set up Node.js
      uses: actions/setup-node@v3
      with:
        node-version: '18'
        cache: 'npm'
    
    - name: Install dependencies
      run: npm ci
    
    - name: Run tests
      run: npm test
    
    - name: Run linting
      run: npm run lint
    
    - name: Build application
      run: npm run build

  deploy:
    needs: test
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    
    steps:
    - uses: actions/checkout@v3
    
    - name: Deploy to production
      run: |
        echo "Deploying to production"
        # Add deployment commands here
```

### 4.7 Advanced Git Topics

#### 4.7.1 Git Hooks
**Client-Side Hooks**
- **pre-commit**: Run before commit creation
- **prepare-commit-msg**: Modify commit message
- **commit-msg**: Validate commit message
- **post-commit**: Run after commit creation

**Server-Side Hooks**
- **pre-receive**: Run before accepting pushes
- **update**: Run for each branch being updated
- **post-receive**: Run after accepting pushes

**Hook Examples**
```bash
#!/bin/sh
# pre-commit hook for code formatting
npm run lint-staged
if [ $? -ne 0 ]; then
  echo "Linting failed. Please fix errors before committing."
  exit 1
fi
```

#### 4.7.2 Git Submodules and Subtrees
**Git Submodules**
```bash
# Add submodule
git submodule add <repository-url> <path>

# Initialize submodules
git submodule init
git submodule update

# Update submodules
git submodule update --remote
```

**Git Subtrees**
```bash
# Add subtree
git subtree add --prefix=<path> <repository-url> <branch>

# Update subtree
git subtree pull --prefix=<path> <repository-url> <branch>

# Push subtree changes
git subtree push --prefix=<path> <repository-url> <branch>
```
