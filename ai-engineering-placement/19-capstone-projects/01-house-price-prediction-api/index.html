House Price Prediction API

Learning Objectives​

ObjectiveDescription
LO1Design and implement a complete ML data pipeline with validation
LO2Build, train, and evaluate regression models with cross-validation
LO3Deploy the model as a FastAPI REST API with Pydantic validation
LO4Add API documentation, testing, and monitoring
LO5Containerize and deploy to cloud platforms
LO6Implement CI/CD for model updates

Prerequisites​

  • Python 3.11 or later
  • Docker 24 or later
  • GitHub account for CI/CD
  • Basic familiarity with pandas, scikit-learn, and FastAPI

What you'll build​

A production-ready house price prediction API that:

  • Ingests raw housing data, validates schema, engineers features
  • Trains multiple regression models (Ridge, Random Forest, XGBoost) with Optuna hyperparameter tuning
  • Serves predictions via FastAPI with automatic OpenAPI docs
  • Includes batch prediction endpoint for bulk scoring
  • Is containerized with multi-stage Docker build
  • Deploys via GitHub Actions to AWS ECS / GCP Cloud Run / Azure Container Instances
  • Monitors prediction latency, error rate, and data drift

import pandas as pd

class DataIngestion:
    """Ingest raw housing data from various sources."""

    def __init__(self, config_path: str = "config.yaml"):
        with open(config_path) as f:
            self.config = yaml.safe_load(f)

    def load_csv(self, path: str) -> pd.DataFrame:
        """Load data from CSV file with validation."""
        df = pd.read_csv(path)
        required_cols = self.config['data']['required_columns']
        missing = set(required_cols) - set(df.columns)
        if missing:
            raise ValueError(f"Missing columns: {missing}")
        return df

    def load_from_database(self, query: str, connection_string: str) -> pd.DataFrame:
        """Load data from SQL database."""
        import sqlalchemy as sa
        engine = sa.create_engine(connection_string)
        df = pd.read_sql(query, engine)
        return df

    def validate_schema(self, df: pd.DataFrame) -> bool:
        """Validate DataFrame schema against config."""
        for col, dtype in self.config['data']['column_types'].items():
            if col in df.columns:
                if df[col].dtype.name != dtype:
                    raise ValueError(f"Column {col} expected {dtype}, got {df[col].dtype}")
        return True

1.3 Feature Engineering​

class FeatureEngineer:
    """Feature engineering for house price prediction."""

    def __init__(self):
        self.feature_names: list = []

    def create_features(self, df: pd.DataFrame) -> pd.DataFrame:
        """Create derived features from raw data."""
        df = df.copy()

        if 'sqft_living' in df.columns and 'sqft_lot' in df.columns:
            df['total_sqft'] = df['sqft_living'] + df['sqft_lot']
            df['lot_to_living_ratio'] = df['sqft_lot'] / (df['sqft_living'] + 1e-6)

        if 'yr_built' in df.columns:
            df['house_age'] = 2025 - df['yr_built']
            df['is_new'] = (df['yr_built'] >= 2015).astype(int)

        if 'bedrooms' in df.columns and 'bathrooms' in df.columns:
            df['rooms_total'] = df['bedrooms'] + df['bathrooms']
            df['bed_bath_ratio'] = df['bedrooms'] / (df['bathrooms'] + 1e-6)

        if 'sqft_living' in df.columns and 'bedrooms' in df.columns:
            df['sqft_per_bedroom'] = df['sqft_living'] / (df['bedrooms'] + 1e-6)

        if 'waterfront' in df.columns:
            pass  # Already binary

        if 'view' in df.columns:
            df['good_view'] = (df['view'] >= 3).astype(int)

        if 'condition' in df.columns:
            df['excellent_condition'] = (df['condition'] >= 4).astype(int)

        self.feature_names = [c for c in df.columns if c.startswith(('total_', 'lot_to_', 'house_', 'is_', 'rooms_', 'bed_bath', 'sqft_per', 'good_', 'excellent_'))]
        return df

    def get_feature_names(self) -> list:
        return self.feature_names


def detect_outliers_iqr(df: pd.DataFrame, column: str) -> pd.Series:
    """Detect outliers using IQR method."""
    Q1 = df[column].quantile(0.25)
    Q3 = df[column].quantile(0.75)
    IQR = Q3 - Q1
    lower = Q1 - 1.5 * IQR
    upper = Q3 + 1.5 * IQR
    return (df[column] < lower) | (df[column] > upper)

1.4 Complete Pipeline​

class DataPipeline:
    """Complete data pipeline: ingest, validate, engineer, split."""

    def __init__(self, config_path: str = "config.yaml"):
        self.ingestion = DataIngestion(config_path)
        self.engineer = FeatureEngineer()
        self.config_path = config_path

    def run(self, data_path: str) -> Tuple[pd.DataFrame, pd.DataFrame, pd.Series, pd.Series]:
        """Run the full data pipeline."""
        df = self.ingestion.load_csv(data_path)
        self.ingestion.validate_schema(df)
        df = self.engineer.create_features(df)

        with open(self.config_path) as f:
            config = yaml.safe_load(f)

        target = config['data']['target_column']
        features = [c for c in df.columns if c != target]

        X = df[features]
        y = df[target]

        X_train, X_test, y_train, y_test = train_test_split(
            X, y, test_size=config['data']['test_split'],
            random_state=config['data']['random_state']
        )

        return X_train, X_test, y_train, y_test

2.2 The trainer​

from sklearn.ensemble import GradientBoostingRegressor, RandomForestRegressor
from sklearn.linear_model import Ridge, Lasso
from xgboost import XGBRegressor
from sklearn.metrics import mean_absolute_error, mean_squared_error, r2_score
from sklearn.model_selection import cross_val_score
import optuna


class ModelTrainer:
    """Train and evaluate house price prediction models."""

    def __init__(self, random_state: int = 42):
        self.random_state = random_state
        self.models: Dict[str, Any] = {}
        self.best_model = None
        self.best_params: Optional[Dict[str, Any]] = None

    def train_ridge(self, X_train: pd.DataFrame, y_train: pd.Series) -> Ridge:
        """Train Ridge regression. Best when features are correlated and scaled."""
        model = Ridge(alpha=1.0, random_state=self.random_state)
        model.fit(X_train, y_train)
        self.models['ridge'] = model
        return model

    def train_random_forest(self, X_train: pd.DataFrame,
                            y_train: pd.Series) -> RandomForestRegressor:
        """Train Random Forest. Handles non-linear interactions, slower to predict."""
        model = RandomForestRegressor(
            n_estimators=200, max_depth=15,
            min_samples_leaf=5, random_state=self.random_state,
            n_jobs=-1
        )
        model.fit(X_train, y_train)
        self.models['random_forest'] = model
        return model

    def train_xgboost(self, X_train: pd.DataFrame,
                      y_train: pd.Series) -> XGBRegressor:
        """Train XGBoost. Strongest baseline on tabular regression."""
        model = XGBRegressor(
            n_estimators=300, max_depth=8,
            learning_rate=0.05, subsample=0.8,
            colsample_bytree=0.8, random_state=self.random_state
        )
        model.fit(X_train, y_train)
        self.models['xgboost'] = model
        return model

    def tune_hyperparameters(self, X_train: pd.DataFrame,
                             y_train: pd.Series,
                             n_trials: int = 50) -> Dict[str, Any]:
        """Tune XGBoost with Optuna. Maximises negative RMSE across 5 folds."""

        def objective(trial):
            params = {
                'n_estimators': trial.suggest_int('n_estimators', 100, 500),
                'max_depth': trial.suggest_int('max_depth', 3, 12),
                'learning_rate': trial.suggest_float('learning_rate', 0.01, 0.3, log=True),
                'subsample': trial.suggest_float('subsample', 0.6, 1.0),
                'colsample_bytree': trial.suggest_float('colsample_bytree', 0.6, 1.0),
            }
            model = XGBRegressor(**params, random_state=self.random_state)
            scores = cross_val_score(
                model, X_train, y_train, cv=5,
                scoring='neg_root_mean_squared_error'
            )
            return scores.mean()

        study = optuna.create_study(direction='maximize')
        study.optimize(objective, n_trials=n_trials)
        self.best_params = study.best_params
        return self.best_params

    def evaluate(self, model, X_test: pd.DataFrame,
                 y_test: pd.Series) -> Dict[str, float]:
        """Compute regression metrics on the held-out test set."""
        y_pred = model.predict(X_test)
        return {
            'mae': float(mean_absolute_error(y_test, y_pred)),
            'rmse': float(np.sqrt(mean_squared_error(y_test, y_pred))),
            'r2': float(r2_score(y_test, y_pred)),
        }

    def train_best(self, X_train: pd.DataFrame, y_train: pd.Series):
        """Train with tuned params if tuning ran, otherwise the XGBoost baseline."""
        if self.best_params:
            model = XGBRegressor(**self.best_params, random_state=self.random_state)
        else:
            return self.train_xgboost(X_train, y_train)
        model.fit(X_train, y_train)
        self.best_model = model
        return model

2.3 Choose between the three metrics​

MetricFormulaWhat it answersUse when
MAEmean absolute error"Typical error in dollars"You talk to stakeholders in currency
RMSEroot mean squared error"How bad are the large misses?"Large errors are disproportionately costly
R²1 − SS_res/SS_tot"How much variance is explained?"Comparing models on the same data

RMSE punishes large errors because it squares them before averaging. MAE does not. If a $50k miss is ten times worse than a $5k miss, optimise RMSE. If it is only slightly worse, optimise MAE.

2.4 Model registry​

class ModelRegistry:
    """Persist trained models with their metadata and evaluation metrics."""

    def __init__(self, registry_path: str = "model_registry"):
        self.registry_path = Path(registry_path)
        self.registry_path.mkdir(exist_ok=True)

    def save_model(self, model, pipeline, metrics: Dict[str, float],
                   version: str = "v1") -> str:
        """Save model, preprocessing pipeline, and metrics under a version tag."""
        model_path = self.registry_path / f"model_{version}.pkl"
        pipeline_path = self.registry_path / f"pipeline_{version}.pkl"
        meta_path = self.registry_path / f"metadata_{version}.yaml"

        joblib.dump(model, model_path)
        joblib.dump(pipeline, pipeline_path)

        metadata = {
            'version': version,
            'metrics': metrics,
            'features': getattr(pipeline, 'feature_names_', []),
        }
        with open(meta_path, 'w') as f:
            yaml.dump(metadata, f)

        return str(model_path)

    def load_model(self, version: str = "v1") -> Tuple[Any, Any]:
        """Load model and pipeline by version tag."""
        model = joblib.load(self.registry_path / f"model_{version}.pkl")
        pipeline = joblib.load(self.registry_path / f"pipeline_{version}.pkl")
        return model, pipeline

Step 3 — Serve the model with FastAPI​

Expose the trained model as a REST API with Pydantic input validation.

3.1 Declare the request and response schemas​

Pydantic validates the request body before it reaches the model, so a malformed payload returns 422 Unprocessable Entity rather than producing a garbage prediction.

from datetime import datetime
from typing import List, Optional, Dict, Any
from uuid import uuid4
import pandas as pd

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field, field_validator


class HouseFeatures(BaseModel):
    """Input features for a single house."""

    bedrooms: int = Field(..., ge=0, le=50, description="Number of bedrooms")
    bathrooms: float = Field(..., ge=0, le=50, description="Number of bathrooms")
    sqft_living: float = Field(..., ge=100, le=50000, description="Living area in sqft")
    sqft_lot: float = Field(..., ge=100, le=500000, description="Lot area in sqft")
    floors: float = Field(1.0, ge=0.5, le=10, description="Number of floors")
    waterfront: int = Field(0, ge=0, le=1, description="Waterfront view (0 or 1)")
    view: int = Field(0, ge=0, le=4, description="View quality rating (0-4)")
    condition: int = Field(3, ge=1, le=5, description="Condition rating (1-5)")
    yr_built: int = Field(..., ge=1800, le=2025, description="Year built")
    yr_renovated: int = Field(0, ge=0, le=2025, description="Year renovated")

    @field_validator('yr_built')
    @classmethod
    def validate_year(cls, v: int) -> int:
        if v < 1800 or v > 2025:
            raise ValueError(f"year out of range: {v}")
        return v


class PredictionResponse(BaseModel):
    """Single-house prediction result."""

    prediction_id: str
    predicted_price: float
    features_used: List[str]
    model_version: str
    timestamp: datetime


class PredictionRequest(BaseModel):
    """Batch prediction request."""

    houses: List[HouseFeatures]


class PredictionResult(BaseModel):
    """One entry in a batch response."""

    predicted_price: float
    house_features: HouseFeatures


class BatchPredictionResponse(BaseModel):
    """Batch prediction result."""

    predictions: List[PredictionResult]
    total_predictions: int
    average_price: float

field_validator vs validator: Pydantic v2 renamed @validator to @field_validator and requires the @classmethod decorator beneath it. If you copy an older snippet using @validator, it raises a deprecation error on Pydantic v2.

3.2 The service and endpoints​

app = FastAPI(
    title="House Price Prediction API",
    description="ML-powered API for predicting house prices from property features",
    version="1.0.0",
)


class HousePriceService:
    """Loads the model once and reuses it across requests."""

    def __init__(self, model_path: str = "model_registry/model_v1.pkl",
                 pipeline_path: str = "model_registry/pipeline_v1.pkl"):
        self.model = joblib.load(model_path)
        self.pipeline = joblib.load(pipeline_path)
        self.model_version = "v1"
        self.prediction_log: List[Dict[str, Any]] = []

    def preprocess(self, features: HouseFeatures) -> pd.DataFrame:
        """Turn the validated request model into the DataFrame the pipeline expects."""
        return pd.DataFrame([features.model_dump()])

    def predict(self, features: HouseFeatures) -> float:
        """Run a single prediction."""
        processed = self.pipeline.transform(self.preprocess(features))
        return float(max(self.model.predict(processed)[0], 0))

    def predict_batch(self, requests: List[HouseFeatures]) -> List[float]:
        """Run predictions for many houses in one pass."""
        frame = pd.concat([self.preprocess(r) for r in requests], ignore_index=True)
        processed = self.pipeline.transform(frame)
        return [float(max(p, 0)) for p in self.model.predict(processed)]

    def log_prediction(self, features: HouseFeatures, prediction: float) -> None:
        """Record the prediction so drift can be detected later."""
        self.prediction_log.append({
            "timestamp": datetime.now().isoformat(),
            "features": features.model_dump(),
            "prediction": prediction,
        })


service = HousePriceService()

3.3 Routes​

@app.get("/")
async def root():
    return {"message": "House Price Prediction API", "version": "1.0.0"}


@app.get("/health")
async def health_check():
    return {
        "status": "healthy",
        "model_loaded": service.model is not None,
        "model_version": service.model_version,
        "timestamp": datetime.now().isoformat(),
    }


@app.post("/predict", response_model=PredictionResponse)
async def predict(features: HouseFeatures):
    """Predict the sale price of one house."""
    try:
        price = service.predict(features)
    except Exception as exc:
        raise HTTPException(status_code=500, detail=str(exc)) from exc
    service.log_prediction(features, price)
    return PredictionResponse(
        prediction_id=str(uuid4()),
        predicted_price=round(price, 2),
        features_used=list(features.model_dump().keys()),
        model_version=service.model_version,
        timestamp=datetime.now(),
    )


@app.post("/predict/batch", response_model=BatchPredictionResponse)
async def predict_batch(request: PredictionRequest):
    """Predict prices for many houses in one call."""
    try:
        prices = service.predict_batch(request.houses)
    except Exception as exc:
        raise HTTPException(status_code=500, detail=str(exc)) from exc
    results = [
        PredictionResult(predicted_price=round(p, 2), house_features=h)
        for p, h in zip(prices, request.houses)
    ]
    return BatchPredictionResponse(
        predictions=results,
        total_predictions=len(results),
        average_price=round(float(np.mean(prices)), 2),
    )

class MonitoringSetup:
    """In-process counters. Swap for Prometheus client in production."""

    def __init__(self):
        self.metrics = {
            "prediction_count": 0,
            "total_latency_ms": 0.0,
            "error_count": 0,
            "drift_alerts": 0,
        }

    def record_prediction(self, latency_ms: float, is_error: bool = False):
        self.metrics["prediction_count"] += 1
        self.metrics["total_latency_ms"] += latency_ms
        if is_error:
            self.metrics["error_count"] += 1

    def average_latency(self) -> float:
        if self.metrics["prediction_count"] == 0:
            return 0.0
        return self.metrics["total_latency_ms"] / self.metrics["prediction_count"]

    def error_rate(self) -> float:
        if self.metrics["prediction_count"] == 0:
            return 0.0
        return self.metrics["error_count"] / self.metrics["prediction_count"]

Interview Q&A​

Q1: How do you handle feature engineering for a house price prediction model?

Five groups of features. (1) Numeric transforms: living area, lot size, and room counts as-is, plus age derived as current_year - yr_built. (2) Categorical encoding: zipcode has high cardinality (100+ values), so one-hot encoding is wrong here — use target encoding (mean price per zipcode) or frequency encoding. (3) Composite ratios: lot_to_living_ratio, bed_bath_ratio, sqft_per_bedroom. These often carry more signal than any single raw column. (4) Location features: latitude and longitude derived from zipcode, then distance to the city centre. (5) Interaction terms: living area minus bedrooms, since a large house with few bedrooms signals luxury.

Validate that engineered features actually help by comparing validation score with and without them, rather than trusting the intuition.

Q2: How do you set up a CI/CD pipeline for an ML prediction API?

Four separate concerns, deliberately split across workflows. (1) CI on every pull request: lint, type-check, and run pytest. Nothing merges without passing tests. (2) Training on a schedule (weekly) or on demand: retrain on all data, log metrics to W&B or MLflow, and register the model only if it beats the current best. (3) CD on model registration: build the Docker image, run integration tests against it, deploy to staging, then promote to production through a canary. (4) Infrastructure as code: Terraform or Pulumi so cloud resources are reproducible rather than clicked by hand.

GitHub Actions or GitLab CI are the usual orchestrators.

Q3: How do you A/B test an ML model deployment?

Three escalating stages. Shadow deployment: mirror a copy of live traffic to the new model, compare its output offline, and serve nothing from it. This catches pipeline bugs with zero user impact. Canary: route 5-10% of traffic to the new model and watch latency, error rate, and prediction distribution against the baseline. Feature flags: once validated, roll forward to 50%, then 100%.

Two details people forget. First, compare both technical metrics (latency, error rate) and a proxy for quality — without ground truth you cannot measure accuracy on new data yet, so watch the prediction distribution for a shift. Second, decide the rollback trigger before you ship: a named threshold like "p95 above 2s for 5 minutes", not a judgement call.

Seven practices, in the order they matter. (1) Multi-stage builds keep compilers and build-only packages out of the runtime image. (2) Pin every dependency version for reproducibility. (3) Bake the model artefact into the image at build time rather than mounting it, so image and model versions cannot drift apart. (4) Run as a non-root user. (5) Add a HEALTHCHECK so the orchestrator can detect a dead container. (6) Use a slim base image. (7) Build the image in CI so a broken Dockerfile fails the pipeline, not production.

Q5: How do you handle model versioning and a model registry for production APIs?

Six elements. (1) Storage: each version gets a unique ID plus its training date, dataset version, hyperparameters, and metrics. MLflow Model Registry and W&B Artifacts are the usual tools. (2) API surface: return the model version in the response so a prediction can be traced back to the model that produced it. (3) Multi-version serving: allow the client to request a version, which is what makes gradual migration possible. (4) Comparison view: metrics per version side by side. (5) Rollback: keep the last three to five versions so switching back is a config change, not a retrain. (6) Promotion gate: a new version only reaches production after automated validation passes on accuracy, latency, and drift checks.

Q6: How do you design FastAPI endpoints for ML model serving?

(1) Input validation via Pydantic Field constraints, so bounds live in one schema instead of being re-checked in every handler. (2) Async endpoints for I/O-bound work, so a slow database call does not block the event loop. (3) A batch endpoint for bulk scoring — amortises per-request model overhead. (4) Custom exception handlers returning consistent JSON error shapes. (5) Middleware for request IDs, CORS, rate limiting, and logging. (6) Free OpenAPI docs; add summary and description to each route so the generated documentation is useful. (7) Cache identical feature sets when they recur.

Q7: How do you monitor prediction drift in a production ML system?

Seven steps. (1) Log every prediction with its input features, predicted value, timestamp, and model version. Nothing below works without this. (2) Compare the incoming feature distribution against training using the KS test for numeric features or the Population Stability Index. (3) Track each feature's min, max, mean, and standard deviation, or its category frequencies. (4) Track the prediction distribution over time. (5) Once ground truth arrives (usually lagged), compute real error and compare it against training performance — this is the only true accuracy signal. (6) Alert when PSI exceeds 0.2 or performance drops more than 10%. (7) Queue an automatic retraining job on sustained drift.

Q8: How does Optuna tune hyperparameters, and what should you watch?

Optuna uses Bayesian optimization with the Tree-structured Parzen Estimator, which models the good regions of the search space and samples there instead of exploring uniformly like a grid or random search. Four practices matter. (1) Define an objective that takes a trial, samples parameters with trial.suggest_*, trains, and returns the validation metric. (2) Use a pruner such as MedianPruner to abandon clearly bad trials early — this often halves the runtime. (3) Search learning_rate on a log scale, because it spans orders of magnitude. (4) Persist the study so a second run continues from the first rather than starting over.

Q9: How do you validate data inside an ML pipeline using Pydantic?

Pydantic v2 validates via type hints and Field constraints, so the schema is the single source of truth: sqft_living: float = Field(ge=100, le=50000). Set ConfigDict(extra='forbid') to reject unknown fields rather than silently ignore them. For cross-field rules use @field_validator — for example flag the combination "more bedrooms than bathrooms on a single floor" as unlikely. For DataFrames, Pandera applies the same constraint model to tabular data.

Q10: What belongs on a monitoring dashboard for a prediction API?

Eight panels. (1) Request volume over time, broken down by endpoint. (2) Latency percentiles — p50, p95, p99 for inference and total request time. (3) Error rate split by cause: validation error, model error, timeout. (4) Prediction distribution histogram, overlaid with the training distribution, so drift is visible. (5) Model version currently serving each request. (6) Cost per hour derived from compute usage. (7) Currently firing alerts with severity. (8) Feature importance, recomputed periodically, since a model whose top feature has gone to zero is suspicious.

Q&A​

How do you handle missing values in the pipeline?

Data preprocessing for regression models.

Branch on column type. Numeric columns use median imputation, which resists outliers in a way mean imputation does not. Categorical columns use the mode, or an explicit "missing" category when absence itself carries meaning. scikit-learn's SimpleImputer handles both inside a Pipeline, which matters because the imputer must be fitted on training data only and then applied unchanged to test data. Skipping the pipeline and imputing the whole frame before splitting leaks test statistics into training.

What is the difference between MAE, RMSE, and R²?

Regression evaluation metrics.

MAE is the average absolute error in the target's own units, so it reads directly as dollars. RMSE squares errors before averaging, so large misses dominate — a model can look fine on MAE and terrible on RMSE. R² is the proportion of variance explained, ranging from negative (worse than predicting the mean) to 1. For house prices, report MAE to stakeholders and RMSE to engineers, because a single large misprediction on an expensive house matters more than several small ones.

How do you encode zipcode for house price prediction?

Feature encoding for location data.

Zipcodes are high cardinality, so one-hot encoding produces hundreds of sparse columns. Four options: target encoding replaces each zipcode with the mean price for that area; frequency encoding replaces it with the number of sales; geographic encoding derives latitude and longitude and adds distance-to-centre; and one-hot is acceptable only below roughly 20 distinct values. Target encoding usually wins for location, but it must be computed on training folds only — computing it on the full dataset leaks the target into the features.

How do you handle high traffic?

API scaling and reliability.

Six levers. Horizontal scaling: several instances behind a load balancer. Caching: identical feature sets recur, so Redis with a TTL removes repeated inference. Rate limiting per client. Async handlers so concurrent requests do not serialise. Batch endpoints to amortise per-request overhead. Autoscaling on CPU utilisation or queue depth. Note that model serving is CPU-bound, so scaling instances usually beats optimising the model.

How do you detect and respond to model drift?

ML model monitoring and maintenance.

Detect three distinct things. Feature drift: incoming feature distributions have moved, measured with KS test or PSI. Prediction drift: the output distribution has moved. Performance drift: once ground truth arrives, actual error has grown. Respond with scheduled retraining on a weekly or monthly cadence, shadow-deploying a new model beside the current one, and rolling back to the previous version when a retrain regresses. Alert thresholds matter more than the exact statistic: PSI above 0.2, or performance down more than 10%.

Common mistakes​

  1. Imputing before splitting. Statistics leak from test into train. Fit the imputer on training data only, inside the Pipeline.
  2. Including id as a feature. An identifier encodes nothing generalisable and lets the model memorise rows.
  3. Skipping validation loss. A model that improves on train while degrading on validation is memorising, not learning.
  4. Reporting only R². R² says nothing about error magnitude in dollars, which is what a stakeholder asks about.
  5. Hardcoding the model path. The container and the trained artefact drift apart. Version the pair together.
  6. Running uvicorn on 127.0.0.1 in Docker. The published port never receives traffic.
  7. Using .dict() on Pydantic v2 models. It raises; use model_dump().
  8. Baking a secret into the image. Model registry credentials belong in environment variables or a secret manager, never in a layer.

Revision notes​

  • Validate input with Pydantic so bad requests fail as 422, not as a wrong prediction.
  • Compare models on MAE (magnitude in real units) and RMSE (large-error sensitivity).
  • Fit every preprocessing step on training data only, inside a Pipeline.
  • Version the model and its preprocessing artefact together.
  • Track prediction distribution over time; it is the earliest available drift signal.
  • Keep the last three to five versions so rollback is a config change.
